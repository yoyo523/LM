# Assignment 2a to 2b implementation decisions

Assignment 2b permits changes, additions, and removals from the 2a design. This record showing the final implemented language and feedback addressed.

## Retained design

The implementation retains typed declarations, pipeline assignment, mandatory braces, strict Boolean conditions, recursive functions, recursive-descent parsing, a positioned AST, scoped semantic checks, bytecode generation, and a stack virtual machine. RISC-V generation remains a potential target from the design, not an implemented backend.

## Feedback addressed with approved extensions

The 2a feedback telling missing arrays, constants, and input, insufficient test expectations, and incorrectly capitalised syntax examples. The following implementation additions were approved in the current maintenance work:

| Feedback | Implemented decision | Evidence |
| --- | --- | --- |
| Arrays absent | `int[]`/`bool[]`, nonempty literals, zero-based indexing, checked indexed assignment, value semantics, typed array parameters/returns | `tests/test_language_extensions.py`, `examples/arrays_constants.kln` |
| Constants absent | `const name: Type = expression;`; assignment to the binding or its array elements is rejected | Extension tests and `examples/invalid/constant.kln` |
| Input absent | `input()` returns one checked signed int32 read from stdin | Extension/CLI sample tests, `examples/input.kln` |
| Expected outputs absent | Separate executable samples and a manifest containing stdin/stdout/exit/diagnostic expectations | `examples/README.md`, `examples/manifest.json`, `tests/test_samples.py` |
| Incorrect example syntax | Lowercase `if`/`while`, semicolon terminators, ASCII minus | Runnable examples and parser rejection tests |

2a sample used `input` as a variable name and that remains valid, only the function-call spelling `input()` denotes the built-in. User functions cannot redefine it. New array operations lower to `BUILD_ARRAY`, `LOAD_INDEX`, and `STORE_INDEX`. Input lowers to `INPUT`. Constant immutability is enforced before bytecode generation. Language reference for exact semantics.

## Clarified behaviour and limitations

Int32 operations trap on overflow and division by zero. Division truncates towards zero. Uninitialised reads and missing returns are runtime errors. Arrays remain one-dimensional. Literals are nonempty; dynamic `array(n, fill)` can produce an empty array when n is zero. No append or slicing is provided;
`len()` reports the current length. Static definite-assignment and all-path-return analysis are absent. VM instruction/frame/heap limits are implemented.

## Advanced rubric implementation additions

After the expanded rubric was supplied, whole-project maintenance added:

- Parametric generic functions with inferred scalar types and typed array forms.
- Runtime-sized `array(length, fill)` allocation and `len()`.
- A VM-owned array heap, root tracing, automatic/explicit mark-and-sweep GC,
  logical memory budget and allocation/reclamation statistics.
- A separate post-semantic optimiser for constant folding and dead-code removal,
  with enabled/disabled execution comparison and inspection controls.

These are additional 2b features, not claims that they existed in the 2a design.
Their grammar, semantics, code paths, tests and limitations are documented in
[advanced features](advanced_features.md). Existing scalar/array value semantics
and checked arithmetic are preserved. Optimisation changes actual instruction
counts, which are measured on the selected generated bytecode.
